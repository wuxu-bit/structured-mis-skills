# Requirements Baseline

## 目标

在绘图之前形成可以审计的分析输入。没有基线就直接画图，最容易造成角色、流程、状态和存储各自演化。

## 输入提取

从需求、调查、访谈纪要或既有成果中提取：

| 类别 | 必答问题 | 基线字段 |
|---|---|---|
| 目标 | 系统解决谁的什么问题 | `system.goal` |
| 边界 | 哪些责任属于系统，哪些属于外部 | `system.boundary` |
| 角色 | 谁发起、处理、审核、接收结果 | `actors` |
| 业务闭环 | 从触发到结果有哪些完整业务 | `businessFlows` |
| 信息载体 | 传递哪些申请、通知、记录和结果 | `dataFlows` |
| 长期信息 | 哪些信息需要反复读写或审计 | `dataStores` |
| 状态 | 哪些对象有生命周期和值域 | `states` |
| 控制点 | 权限、审核、并发、异常、申诉 | `requirements` |
| 外部依赖 | 支付、身份、通知等边界系统 | `actors` |
| 排除项 | 当前明确不做什么 | `system.exclusions` |

## 需求编号

每条可验证需求使用稳定编号，例如 `R-001`。一条需求只表达一个可验证义务：

```json
{
  "id": "R-001",
  "statement": "已认证读者可以提交借阅申请",
  "source": "confirmed requirement",
  "priority": "must",
  "status": "accepted"
}
```

禁止使用“实现完整用户管理”等无法验证的宽泛表述。

## 边界判定

外部实体必须位于系统控制边界之外。人员、部门和外部系统可能是外部实体；系统内部模块不是外部实体。判断顺序：

1. 本系统是否控制其内部规则和数据？
2. 它是否只向系统提交或接收数据？
3. 需求是否明确把它定义为外部依赖？

边界不确定时进入 `openQuestions`，不要同时把同一对象画成外部实体和内部处理。

## 业务闭环判定

合格闭环至少包含：

- 触发者；
- 业务目标；
- 输入信息；
- 核心处理；
- 正常结果；
- 关键异常；
- 状态变化；
- 必要留痕；
- 终止或转交条件。

按闭环划分，不按“新增页、编辑页、列表页”划分。

## Gate 输出

开始绘图前输出一份基线摘要和未决问题。用户确认或资料足够后，才能进入TFD建模。
