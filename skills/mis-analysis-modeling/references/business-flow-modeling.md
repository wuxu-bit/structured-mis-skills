# Business Flow Modeling (TFD)

## 语义目标

TFD描述现实业务作业顺序、参与单位、流转单据和存档关系。它回答业务如何流转，不解释软件组件如何实现。

## 可配置符号 Profile

本 Skill 默认提供 `academic-tfd`：

| 语义 | draw.io形状 | 命名 |
|---|---|---|
| 人员、部门、外部处理单位 | 正圆 `shape=ellipse` 且宽高相等 | 职责名词 |
| 业务处理 | 普通矩形 | 动词+业务对象 |
| 申请、通知、清单、结果单 | Document | 业务对象+载体类型 |
| 长期档案、日志、记录集合 | Stored Data | 业务对象+档案/日志 |
| 信息传递 | 有向正交线 | 默认无边标签 |

不同教材可能使用不同符号和边标签规则。先在 `notationProfile` 中声明，再校验。不要把学校特定图号或符号冒充通用标准。

## 建模顺序

1. 写出本图业务目标和边界。
2. 列出发起者、处理单位和接收者。
3. 列出触发申请、处理中间单据、结果通知和长期存档。
4. 先构建正常主干。
5. 对每个判断点补充失败、驳回、补正、重试、超时和取消。
6. 对审核、处罚、资金、权限和状态变化补充审计记录。
7. 确认每个处理有输入和输出。
8. 确认图题中的每个阶段真实出现在图内。

## 结构约束

- 处理与信息载体应形成可解释的输入输出关系。
- 避免多个处理连续直连；缺少信息载体时先核实业务语义。
- 申请、通知和档案之间不应无处理直接转换。
- 处理不能成为悬挂末端。
- 异常分支必须到达接收者、后续处理、存档或明确终止点。
- 重试必须回到明确入口，不能画成自由端点。
- 同一角色或存档可重复显示以改善布局，但名称和含义必须一致。

## 无边标签 Profile

若采用“箭头不写文字”规则：

- 所有 edge `value` 必须为空；
- “通过/驳回”“成功/失败”等含义通过结果单或通知节点表达；
- 保存、登记、发送等语义用处理节点表达；
- 不允许两条无名分支仅靠位置表示“是/否”。

示例：

```text
读者 → 借阅申请单 → 检查借阅资格
检查借阅资格 → 借阅批准单 → 登记借阅记录
检查借阅资格 → 借阅拒绝通知 → 读者
```

## 异常检查矩阵

按适用性检查：

| 类别 | 示例 |
|---|---|
| 信息质量 | 缺字段、格式错误、材料不完整 |
| 身份权限 | 未认证、账号受限、角色不符 |
| 状态冲突 | 对象已关闭、已锁定、已处理 |
| 重复并发 | 重复提交、并发占用、幂等冲突 |
| 人工决定 | 驳回、补正、复核、调整决定 |
| 外部依赖 | 外部系统失败、回调异常 |
| 时间 | 超时、到期、逾期 |
| 主动操作 | 取消、撤回、重新提交 |
| 治理 | 举报、申诉、补偿、留痕 |

并非每张图必须机械包含全部异常，但省略核心异常必须说明边界。
