# Data Flow Modeling (DFD)

## 语义目标

DFD描述系统边界内外的数据来源、去向、加工和逻辑存储。它不表达页面顺序、按钮点击、程序调用或物理数据库细节。

## 元素与编号

默认编号空间：

| 元素 | 编号 | 名称规则 |
|---|---|---|
| 外部实体 | `S1`, `S2` | 角色、组织或外部系统名词 |
| 总处理 | `P0` | 系统名称 |
| 第一层处理 | `P1`... | 功能域名称 |
| 子处理 | `P1.1`, `P1.1.1` | 动词+业务对象 |
| 数据存储 | `F1`, `F2` | 业务对象+档案/记录/日志 |
| 数据流 | 稳定ID与可见名称分离 | 名词性数据对象 |

字典卡片编号必须使用独立命名空间，例如 `E-01`、`P-01`、`DF-01`、`DS-01`、`ST-01`、`DI-01`，避免把图上 `F1` 数据存储与字典卡片编号混淆。

## 分层流程

### 顶层图

- 只画一个总处理、外部实体和边界输入输出。
- 不画内部数据存储。
- 用于确认系统边界，不展示内部模块。

### 第一层图

- 将总处理拆成3至7个主要处理。
- 引入核心逻辑数据存储。
- 覆盖顶层全部边界输入输出。
- 处理之间只通过有名称的数据流交互。

### 第二层图

- 每张子图展开一个第一层父处理。
- 保留该父处理的全部边界输入输出。
- 可显示相邻处理占位符，但不能展开相邻处理内部细节。

### 第三层图

- 仅继续展开仍然复杂的父处理。
- 子处理编号必须继承父编号。
- 新增内部细化流可以存在，但新增边界流必须有父流映射或变更记录。

## 基本正确性

- 每个处理至少一条输入和一条输出。
- 每条数据流至少一端连接处理。
- 禁止外部实体—外部实体直连。
- 禁止数据存储—数据存储直连。
- 禁止外部实体—数据存储直连。
- 数据流必须是数据对象，不是“下一步”“通过”“返回”等控制词。
- 数据存储表示长期保存、可被反复访问的数据集合。
- 全套模型中每个逻辑存储至少有读取和写入。

单张子图中的跨域参考存储可以只读，但必须在模型中声明，不能为了形式制造无意义的“写后立即读”。

## 父子图平衡

对父处理 `P` 定义边界集合：

```text
B(P) = {(逻辑端点, 方向, 数据流语义)}
```

对子图收集所有子处理与外部实体、数据存储及非子处理占位符之间的边界流。匹配结果分为：

| 结果 | 含义 |
|---|---|
| exact | 端点、方向、语义完全一致 |
| refined | 一条父流被显式拆成多条子流 |
| missing | 父流在子图缺失 |
| added | 子图新增未解释边界流 |
| reversed | 数据方向反转 |
| endpoint-changed | 外部端点被替换 |
| alias-unresolved | 名称相近但没有映射依据 |

副本按逻辑编号归一化，不按 draw.io `mxCell id` 重复计数。

## 跨域数据

区分：

1. 业务事件跨域，例如“订单状态变更通知”；
2. 共享数据读取，例如订单处理读取用户资格；
3. 治理联动，例如违规处理改变商品状态。

跨域事件优先连接同级处理占位符。不要用管理员外部实体替代平台治理处理的输出，也不要让子图通过长线绕过父层接口。

## TFD到DFD重构

| TFD元素 | DFD转换 |
|---|---|
| 业务处理 | 通常转为数据处理 |
| 单据、通知、报表 | 通常转为数据流 |
| 长期档案 | 通常转为数据存储 |
| 外部业务单位 | 边界外则转为外部实体 |
| 无标签顺序线 | 改写为有名称的数据流 |

转换不是机械复制。TFD强调业务作业，DFD强调数据加工。
